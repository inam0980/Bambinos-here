Paid Is Not Scheduled

Re-engineering the Bambinos.live Student Renewal → Class Scheduling pipeline · AI Program Manager (Operations) take-home · Nov 2026
Prototype + data + outputs: see GitHub repo (README). Analysis run on the provided 5-table dataset, snapshot as of 2026-11-04 09:00.
One-line thesis. The pipeline treats the teacher's form as the trigger and the payment as something to verify. It should be the other way round. The gateway already knows who paid, how much, for which student, class and teacher. For a same-batch renewal (the majority) Steps 2 and 3 add no information, only delay and typos. Remove them, let the ledger drive scheduling, and send humans only the cases that genuinely need judgement.

A2. Failure-mode taxonomy (beyond this sample)

  • Trigger failures: teacher forgets, is on leave, or files late (orphaned invoices). Weekend and late-evening payments wait until Monday because Ops is offline. Two of 13 payments here came in on a Sunday.
  • Identity failures: a different payer phone or email, siblings under one parent account, NRI numbers (+971, +1), look-alike characters, masked PII.
  • Money failures: partial or installment payments, failed or pending UPI, unapproved discounts, currency mismatches (US/GCC), refunds or chargebacks after scheduling.
  • Data-entry failures: wrong invoice ID or link, wrong amount, wrong batch, duplicate submissions.
  • Scheduling failures: the "batch full" logic counts the renewing child, batch changes are approved without a feasible slot, and parents don't answer slot-selection messages (open loop).
  • Continuity failures: the old term ends before the new bookings exist, so the child misses classes even though the parent paid. This is the failure the parent actually feels.
  • Visibility failures: no stage timestamps or owner, so nobody can see "paid 3 days ago, still nothing".

Hours saved: today each renewal costs about 20 min of manual work (teacher form ~6, Ops verification ~8, allocation ~6) plus ~10 min of chasing per exception. Assuming ~400 renewals a week and 70% straight-through: 280 × 20 min ≈ 93 h/week saved. Exceptions arrive pre-diagnosed, so ~10 min saved on each of 120 adds ~20h. Net ≈110 h/week ≈ 2.5–3 FTE of a 10-person Ops team, redeployed to exception handling and parent experience. Teachers save ~40 h/week of form-filling. (Assumptions to validate in the first 30 days by time-and-motion sampling.)

D3. Change management: rolling out without breaking live classes

  • Shadow mode first. The engine runs alongside the manual process and writes to a shadow table. Ops keeps working as today. Every day we compare engine decisions with human decisions and target ≥98% agreement before switching on.
  • Never delete a seat. In every mode, an existing student is never removed from the current batch until the new bookings are written. That rules out class gaps by design.
  • Kill switch and rollback. A single config flag sends everything back to the manual queue. Auto-approvals are reversible for 24h.
  • Teachers: the message is "you no longer need to fill a form", which removes work, so adoption is easy. Pilot with 20 high-renewal teachers, then onboard in waves through 10-minute WhatsApp voice notes and a pinned FAQ. The Teacher League rewards teachers, it doesn't name and shame them.
  • Ops team: roles move from "verifier" to "exception specialist". Two Ops champions co-own the rule book, and nobody is made redundant in the first 90 days.

Risks & mitigations

  • Wrong auto-approval: approval only ever happens on gateway Paid + an ID match. Everything is logged and reversible, and the shadow period proves accuracy first.
  • Webhook outage: a 15-minute polling reconciliation catches up, and the board shows the time of the last successful sync.
  • Bad LLM messages: templates are the default. The LLM only rewrites tone, and numbers are checked in code.
  • PII: data stays masked and only IDs go to the LLM. WhatsApp sends use approved templates only.
